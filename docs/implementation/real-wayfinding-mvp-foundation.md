## 2. What changed

### Navigation Pilot V2 + Spatial Data Layer V1 (recovered, unchanged in behaviour)
Destination-first search-as-you-type over 5 real tenant identities + 4 schematic amenities,
changeable start, summary tiles, step mode, mobile-first layout, honest preview messaging,
`PilotAnchor` positioning seam; dataset JSON + typed contract + validator + adapter with
per-entity evidence (`schematic | source-backed | on-site-verified`) and tenant identity
evidence kept separate from spatial evidence.

### Navigation entry point (shopper journey)
- `src/components/navigation/WayfindingPilot.tsx` — the V2 experience extracted into **one shared
  component**. Mounted embedded on the **Navigate tab** (`NavigateScreen.tsx`, no active route →
  "Where do you want to go?") and standalone at `/pilot` (`MallRedsPilot.tsx`, controlled testing).
  No diverging implementations.
- `NavigateScreen.tsx` route view kept for assistant-built routes; the **simulated walk-through
  (animated marker, Start/Pause/Reset, "Navigating"/"Simulating" labels) was removed** from the
  shopper build. Five stacked badges replaced by one status: "Preview · position not tracked".
  `routeWalk*.ts` modules and tests remain (frozen, unused by shoppers).
- "New" now returns to the finder instead of product search.

### QR-ready start anchor (URL seam)
- `src/components/navigation/wayfindingAnchor.ts` — `parseWayfindingAnchor(search)` for
  `/navigate?mall=mallreds-pilot&start=entrance-main` (and `/pilot?…`). Strict: mall must have a
  bundled dataset, start must be an allowed start node (entrance/landmark). Invalid → `anchor: null`
  + human reason → UI shows a notice and **manual start selection still works**. A URL can never
  place the shopper at a node the dataset does not know.
- Same `PilotAnchor` model as manual selection; `source` gains `"url"` (`"qr"` reserved for a real
  scanner). UI labels the start "from your link" and lets the shopper change it.
- `wayfindingLinkFor(mallId, startNodeId)` builds the canonical link a printed QR should encode.

### Route truthfulness (backend)
- Audit finding **confirmed**: `routingService.ts` inserted a fabricated 100 m
  `"Head to X on Floor ?"` step when Dijkstra found no path (both `buildRoute` and
  `buildRouteNoSession`), and `geminiService.buildFallbackRouteSteps` gave every stop 100 m and a
  default "Floor G".
- Fix: pure planner extracted to `services/routingCore.ts`. Any unreachable leg fails the **whole**
  plan with `fallback: true`, `fallback_reason: "no_graph" | "destination_not_in_graph" |
  "no_path"`, `unroutable_destinations: [...]`, zero steps, zero distance, zero minutes, and the
  route is **never persisted**. Assistant fallback steps are now a store list with `distance 0`,
  floor `null` when unknown, and summary "· directions unavailable".
- Callers: `routes/buildRoute.ts` (shape extended, backwards compatible), `geminiService.ts`
  (summaries no longer say "~0 min walk"), frontend `BuildRouteResponse` unchanged fields.
- Regression harness `services/__tests__/routingServiceHarness.ts` (28 checks) wired into
  `verify:all` as "Routing truthfulness harness".

### PWA / phone readiness
- `public/icons/icon-192.png`, `icon-512.png` (+ maskable) generated by
  `scripts/pwa/generate-icons.mjs` (pure Node, reproducible); manifest and `apple-touch-icon` wired;
  Lovable OG images removed.
- `public/sw.js`: versioned caches (`mallmind-v3-…`), **network-first for navigations** with
  offline shell fallback (fixes the stale-shell pin), cache-first for hashed `/assets/*`,
  stale-while-revalidate for other same-origin GETs, cross-origin never intercepted.
- Home capability strip: "Verified prices / Smart routes / AI powered" → "Store finder / Route
  preview / AI assistant"; "verified data" and "verified picks" copy corrected.

### Type safety
`tsc -p tsconfig.app.json` had **26 errors** (the audit counted 9 by file group): 12 stale
`@ts-expect-error` directives on `.mjs` imports, 4 test fixtures missing `observedAt`, 6 missing Web
Speech API types, 2 `PromiseLike.catch`, `ProductResult.category`, a `finding_type` union narrow and
a `MallHealthReport` cast. All fixed without `any` / `@ts-ignore`; Web Speech types added as
`src/types/web-speech.d.ts`. `npm run typecheck` is now the second step of `verify:all` (and thus
CI).

## 4. Spatial dataset readiness

Question asked: *what is the minimum shape to load ONE real traced route as JSON without rewriting
the app?* Answer: the existing contract (nodes with `x_percent/y_percent`, edges with measured
`distance_meters`, evidence per entity) already carries a route. The one genuinely missing field was
a reference to **the plan the coordinates were measured on**. Added, optional, per floor:

```json
"floors": [{ "id": "G", "label": "Ground Floor",
  "plan_image": { "url": "/plans/mallreds-ground.png", "width_px": 2000, "height_px": 1240,
                  "evidence": "source-backed", "source": "…", "licence": "…" } }]
```

Validator enforces the MallMind plane aspect 1000:620 (±2 %) so the existing renderer draws the
plan 1:1 under the graph; `attachFloorImages()` puts it on the model. Also validated now: floors
non-empty, unique, every node on a declared floor. **Not added**: metres-per-pixel, bearings,
polylines, IMDF/IndoorGML, any migration. Mall@Reds declares no `plan_image` and remains schematic.

## 7. Known limitations
- Instruction text still has no left/right turns (needs edge bearings, deliberately deferred).
- Rate limiting is per Cloud Run instance (in-memory); adequate for a pilot, not for scale.
- Migration 042 is verified on a rebuilt local database in CI; the hosted project must have it
  applied and its drifted policy set checked.
- `/pilot` is unlinked by design (testing mount). The Navigate tab is the shopper entry.
- One mall only (`mallreds-pilot`); `knownWayfindingMalls()` is the registry to extend.
